# Changelog

## Unreleased

- Added the discovery runner panel, so the backend runner merged in RUNNER-EXEC-001 is finally reachable from the workspace. It starts a run from the live dataset and strategy over one parameter axis, shows the projected candidate count, and exposes pause, resume, cancel, and an explicit re-query. The random seed is generated but **displayed and editable**, because a run's whole Random Entry distribution derives from it and reproducing a run means re-entering it; the holding allowance is likewise an explicit field rather than a hidden default. Two rules shape the panel: the database is the source of truth, so it adopts whatever run already exists via `get_active_discovery_run` on mount — which is how a run that startup recovery left paused is rediscovered after a window reload — and events are only a fast path layered on that snapshot; and one monotonic sequence guard covers all three channels, so an out-of-order or replayed event is ignored and a coalesced progress tick can no longer overwrite the terminal status. Progress is throttled and the throttle is cancelled on unmount. Because cancelling it also drops whatever tick was still queued, a terminal event now re-reads the authoritative counts from the database instead of reconstructing them from whichever events survived coalescing. A payload the parsers reject is surfaced as a zh-TW "the view may be behind the database, re-query" notice rather than swallowed, and a run is validated through the shared admission parser before any command is called, so an invalid axis, seed, or strategy fails in the panel with no run row created. Results are listed newest-first, deduped by sequence, and a gate-failed candidate shows no score rather than a zero. The `?mock=1` seam gained a fake runner that emits real `discovery-event-v1` payloads through the production subscriptions and parses them with the production parsers, so the browser tests exercise the whole chain; its two DEV-only knobs pace the simulated candidates and pre-create a paused run so recovered-run adoption is observable.
- Added the frontend assembly of a discovery run's `discovery-config-v1` envelope, validated before anything is invoked. Starting a run requires the full admission envelope — thirteen exact keys, ten pinned contract versions, the dataset identity, a base preset with its axes, complete Gate and Score configs, an explicit seed, and the caps — so building it inside a component would have meant a second, drifting copy of a contract the backend rejects wholesale. The builder assembles it from the modules that already own each part and then validates the result with the same admission parser the Rust side mirrors, so a malformed run fails in the workspace with a path-qualified message and no run row is ever created; the indicator-parameter rules therefore reach discovery for free. Everything derivable is derived rather than asked for: the contract versions and the Gate/Score defaults are copied from their owning constants, and the benchmark costs follow the base strategy because the envelope requires the two to agree. Concurrency is always left to the backend, which resolves it with its own core count. The seed and the holding allowance stay explicit inputs with no hidden defaults, since a run's whole Random Entry distribution derives from the seed and reproducing a run means re-entering it. The strategy is deep-cloned into the envelope, so a later edit cannot change what a submitted run recorded. Nothing is wired to a command or a screen yet.
- Replaced the frontend discovery-event definitions with the real `discovery-event-v1` contract and pinned it from both languages. The previous definitions were written before the backend runner existed and matched **none** of the emitted fields — they expected `tested`/`total`/`skipped` and a `current: { symbol, interval, segment }`, while the runner emits `eventVersion`, `sequence`, `counts`, an optional candidate digest with paired job ids, `strategyHash`, `validationRecordId`, `gatePassed`, `score`, and a terminal `status`/`errorMessage`. Nothing imported the stale file, so the drift was invisible; the first UI built on it would have rendered `undefined` for every value. One authored fixture (`fixtures/rs-core/discovery-event-v1.json`) now holds a sample of every event variant, including the two opposite optional-field conventions the payloads really use — `candidate`/`bestStrategyId`/`errorMessage` are omitted keys while a gate-failed `score` is an explicit `null` — and both sides assert against it: Rust compares its serialized structs to the samples, TypeScript parses the same samples, so a field added or renamed on either side fails the other side's test. Incoming payloads are now parsed rather than trusted: a wrong or missing contract version, a missing required key, a wrong runtime type, an integer outside the JavaScript safe range, or a present-but-malformed optional is dropped and reported through an explicit invalid-payload hook instead of reaching the UI as `undefined`. The two "no value" conventions are kept distinct because the difference is load-bearing: an omitted `candidate`/`bestStrategyId`/`errorMessage` key is the contract, whereas `score` is always emitted and only its value is nullable, so a result payload missing that key is malformed rather than score-less; `gatePassed` and `score` must also agree, matching the CHECK constraint the validation-record table already enforces. `get_active_discovery_run` gained the typed wrapper it never had (the only way to rediscover a run that startup recovery paused), and `get_discovery_progress` is no longer typed `unknown`. The progress throttle is now cancelable and stale-timer-safe: a queued trailing call is dropped on cancel instead of firing into an unmounted view, and a payload can no longer be delivered twice when the window reopens before its queued timer runs — invisible for a progress counter, but a double-appended row for a results list. No emitted payload, event name, command name, or command signature changed.
- Added one runtime admission gate for a manual strategy's indicator parameters, so a value that cannot produce an indicator series is rejected instead of silently becoming a confident zero-trade result. `fastMA: 2.5` previously reached `sma()`, where `values[i - 2.5]` is `undefined` and poisoned every subsequent value into `NaN`; `0` and negative periods took the early-return path to the same outcome, and the resulting "successful" backtest could be saved, hashed, and exported. The eight period fields now require safe integers `>= 1`, `rsiBuy`/`rsiSell` must stay within 0–100, and `bbMult` must be positive — enforced at the execution boundary (`runParamsBacktest`, which also covers every parameter-sweep variant, so an unevaluable combination becomes an empty heatmap cell rather than a zero-trade score) and at the persistence boundary (`buildStrategyDef`, before a durable `strategy-v2` identity can exist). The Run button now explains which field is wrong, the indicator inputs gained `min`/`step` hints as secondary protection, and the three cross-field hypothesis rules the discovery enumerator prunes (`fastMA<slowMA`, `macdFast<macdSlow`, `rsiBuy<rsiSell`) are shown as warnings without blocking, because they are computable and merely dubious. The five execution-model fields keep their documented legacy clamping (`sizePct: 0` still means 100%, a negative fee still clamps to 0), and a strategy saved before this contract still loads into the editor so it can be repaired. The shared rule set was not duplicated: the numeric domain table, `checkNumericParam`, and the cross-field rules moved verbatim out of `discoveryConfig`/`candidateEnumeration` into the new validator, which those modules now re-export from — behaviour, wording, and every consumer unchanged.
- Bound every completed parameter sweep to the inputs it optimised over, so a heatmap can no longer be applied to a strategy or a bar range it was not computed for. A finished sweep is now one frozen artifact (`sweep-context-v1`) carrying the dataset id and content hash, symbol, interval, time range and bar count, the exact optimised range including the Holdout split, the normalized sweep configuration, and the base strategy with the swept axes masked out; one canonical context comparison decides whether it still describes the live inputs. Toggling Holdout, moving its percentage, switching dataset, or editing any strategy field the sweep held constant now removes the heatmap, the apply-best button, and the applied-cell highlight in the same render that accepts the edit, and says a re-scan is required. Previously only a sweep-config edit or a library load cleared the grid, so a full-period heatmap stayed appliable after Holdout was switched on — quietly tuning the strategy on the bars reserved as out-of-sample. Applying a cell of a swept axis deliberately keeps the grid valid, because those are the only parameters the heatmap changes. The sweep also carries a generation token, so a late completion whose inputs are no longer live is discarded without leaving either a grid or an error. The sweep engine, its axis/combination caps, its metric projection, and the in-sample optimisation boundary are unchanged, and the artifact is in-session UI provenance only — no schema, migration, or persisted row was added.
- Added a market-data admission contract (`market-data-quality-v1`) so dataset identity is no longer mistaken for dataset validity: an epoch-seconds timestamp, a non-positive price, a negative volume, or an inverted high/low bar can no longer be imported, and data stored before the contract existed now fails closed instead of producing confident, persisted, wrong evidence. One ordered rule set — plausible epoch-millisecond timestamps inside `2000-01-01T00:00:00Z` (inclusive) to `2100-01-01T00:00:00Z` (exclusive), independently asserted date representability, strictly positive OHLC prices, non-negative volume, `high >= low`, and `low <= open/close <= high` — is implemented once per language and enforced at four call sites: the TypeScript import boundary (covering the real and mock clients), the dataset-selection candle load, the Rust import path before its transaction is opened, and the discovery runner's dataset load after identity verification. Datasets are admitted whole or rejected whole; invalid stored candles are never repaired, dropped, or re-hashed, and the user re-imports. A rejected discovery start writes nothing at all — no run row, job, progress, event, or coordinator control — and a paused run stays paused on a rejected resume. **The dataset hash preimage, its version string, and the committed identity fixture are unchanged**, and no schema, migration, or dependency changed. TypeScript and Rust are locked to one authored accept/reject fixture, including the four range-boundary rows; the contract is documented in `docs/market-data-quality-contract.md`, which also records that rule 1 is structurally unreachable at the import mount point because the pre-existing identity safe-integer check fires first. The intentionally accepted unknown-interval fallback is untouched and remains `INTERVAL-CONTRACT-001`.
- Prevented a second desktop process from running SQLite initialization or orphan recovery against a live discovery run by registering Tauri's official single-instance plugin before `setup`. A secondary launch now exits cleanly after restoring, unminimizing, and focusing the primary main window. The dependency is desktop-target-only, the declared Rust floor is updated to 1.77.2 to match the plugin MSRV, and regression tests lock both the focus sequence and plugin-before-recovery ordering. A Windows two-launch native smoke proved the second process exits with code 0, only one binary remains, a live `running` row is not paused/requeued, and a minimized primary becomes the foreground window.

A recursive mutation matrix removes every present required DTO field from real runner output and proves each mutation fails closed; existing `validation-record-v1` rows remain readable legacy evidence with an unknown metrics formula.
